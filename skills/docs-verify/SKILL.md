# Verify documentation against the code

You are checking documentation that was generated by another session. Assume nothing in it is correct until you have checked it against the code. An engineer is supervising this run.

Agent files are installed at `__AGENT_HOME__`.

## Step 0 – Rules

Read `__AGENT_HOME__/RULES.md` in full and follow it for the rest of this run.

Ask the engineer whether to verify **everything** (after a bootstrap) or only **the sections changed on this branch** (after a refresh). For changed sections only, list them with:

```
git diff --name-only
python3 __AGENT_HOME__/scripts/markers.py list
```

and compare the section bodies with `git diff` to find the ones that changed.

## Step 1 – Deterministic checks

Run:

```
python3 __AGENT_HOME__/scripts/check_citations.py --json
python3 __AGENT_HOME__/scripts/markers.py check
```

Fix every broken citation first: find the right line, or replace the claim with an `Unknown` item.

## Step 2 – Check each claim

For every section in scope, and for every claim in it:

1. Open the cited file at the cited lines.
2. Decide whether the code **supports** the claim:
   - **Supported:** the code says what the docs say. Leave it.
   - **Partly supported:** correct the wording so it matches the code exactly.
   - **Not supported:** remove the claim, or replace it with an `Unknown – needs SME input` item.
   - **Not cited:** find evidence and add a citation, or replace it with an `Unknown` item.
3. Check that nothing reproduces a secret value, personal data or an internal hostname.
4. Check that `Inferred` labels are used wherever the text goes beyond what the code shows.

When you change a section, set its marker back to `commit=PENDING`. Only change content inside markers.

Keep a tally: claims checked, supported, corrected, removed or converted to `Unknown`.

## Step 3 – Coverage

Compare the docs with `.docs-agent/facts.json`. If the facts file is missing or out of date, run `python3 __AGENT_HOME__/extractors/extract_facts.py` first. List anything significant that the docs don't mention:

- environment variables in `environment_variables`
- routes in `routes`
- models and migration folders in `data`
- CI workflows and jobs in `ci`
- platforms in `infrastructure` and `containers`
- external services in `integrations`

Add missing items to the right sections, with citations. If there are too many to add, list them in the report as gaps.

## Step 4 – Final checks

Run:

```
python3 __AGENT_HOME__/scripts/markers.py stamp
python3 __AGENT_HOME__/scripts/check_citations.py
python3 __AGENT_HOME__/scripts/check_output.py
```

All three must pass. `check_output.py` reports locations, not values. Fix every error it reports. If you believe something it flags is a false positive (for example a public, generic service mailbox), explain why to the engineer and let them decide. Do not work around the check.

## Step 5 – Report

Write `.docs-agent/verification-report.md`. This file is local and not committed. Use this structure:

```markdown
# Verification report

- Repository: <directory name>
- Source commit: <from markers.py list>
- Agent version: <from markers.py list>
- Scope: full baseline | sections changed on this branch

## Results
| Measure | Count |
|---|---|
| Sections checked | |
| Claims checked | |
| Supported as written | |
| Corrected | |
| Removed or converted to Unknown | |
| Unknown items (total) | |
| Inferred items (total) | |
| Broken citations remaining | 0 |
| check_output.py | PASSED |

## Gaps
<coverage gaps not fixed in this run>

## Questions for SMEs
<every Unknown item, as a numbered list with its page, so it can be pasted into an SME session agenda>

## PR description
<a short block the engineer can paste into the PR: what was generated, the counts above, and how reviewers should review it (check the Unknown questions, spot-check citations)>
```

Then report to the engineer as described in section 8 of the rules, and point them to the PR description block.
